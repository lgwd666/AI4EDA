# P0 日间学习 03：模拟器与 DiffTest

> 建议用时：20~25 分钟。本单元不需要服务器。
>
> 学完目标：能解释模拟器的主循环、DUT/REF 的职责，以及 DiffTest 为什么能缩小调试范围。

## 1. 模拟器也是一个状态机

指令集模拟器不是“假装打印几条日志”，而是用软件维护 ISA 状态，并逐条执行状态转移。

一个最小主循环可以抽象为：

```text
while 尚未遇到 ebreak:
    1. 从当前 PC 指向的内存取出指令
    2. 译码，得到操作类型、寄存器编号和立即数，并读取 rs1/rs2 的值
    3. 保存旧 PC
    4. 执行运算或访存，并按指令类型决定下一 PC
    5. 统一提交寄存器、内存和 PC 的变化
```

P0 里用 `ebreak` 作为停机约定，DUT/REF 看到它都应停止。P0 的 minirvEMU 只实现 8 条指令，但其主循环骨架与完整 RV32IM 模拟器相似；完整实现还要扩展其他分支与跳转、乘除法、异常和调试功能，P1 的 NEMU 会大得多。

实现时尤其要小心 PC：P0 的普通指令默认前进 4，`jalr` 则覆盖为跳转目标；`rd` 所需的返回地址来自当前指令的旧 PC，而不是更新后的 PC。完整 RV32I 中，分支和 `jal` 也会改变下一 PC。

## 2. DUT 和 REF 分别是什么

P0 最早的 DiffTest 雏形是 **sCPU ↔ sEMU**。下面的 **minirv NPC ↔ minirvEMU** 是同一方法的延伸，可作为 P0 选做或 P2 预演，不影响先完成 sCPU ↔ sEMU：

- **DUT（Device Under Test）**：被测设计，也就是用 RTL 实现的 minirv NPC。
- **REF（Reference Model）**：参考模型，也就是按同一 ISA 规则运行的 minirvEMU。

```text
                 相同程序和初始状态
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
        RTL NPC（DUT）            minirvEMU（REF）
             │                         │
             └────── 比较体系结构状态 ──┘
                          │
                    首个差异即报错
```

REF 不是“永远正确的真理”。它是另一份实现，同样可能写错；P0 里两份实现都由你自己完成，独立性也有限。价值在于：两个不同实现若对同一输入产生不同结果，就给出了一个需要调查的明确位置。

## 3. DiffTest 怎样工作

一种适合当前单周期/迷你处理器的比较流程是：

1. 给 DUT 和 REF 装载相同程序，并设置一致的初始状态。
2. 让 DUT 完成并提交一条指令。
3. 让 REF 执行对应的一条指令。
4. 在指令提交（retire，退休）边界比较退休后的下一 PC、通用寄存器，以及定义好的内存写入事件；两端必须采用同一个 PC 定义，日志建议同时打印旧 PC 和下一 PC。
5. 如果出现差异，立即停止并报告当前指令和状态；否则继续下一条。

这种逐条对齐的方式常称为**锁步（lockstep）比较**。关键是**对齐比较边界**。流水线内部信号、某个中间周期的寄存器值，未必能和模拟器的逐步执行一一对应；应该先比较指令退休后软件可见的体系结构状态。

内存也不必每执行一条指令就完整复制比较一遍。可以先记录 store 的地址、数据和字节使能，在明确的事件边界检查副作用；具体方案由后续实验根据接口决定。若 LSU 接口方便，也可用 mtrace 记录 load 地址；否则要明确“load 地址算错但碰巧读到相同数据”是当前比较集合的盲区。

## 4. 为什么比单纯看波形高效

假设 DUT 错误地把 `addi` 的 12 位立即数做了零扩展：

```asm
addi x1, x0, -1
```

正确 REF 与错误 DUT 的结果为：

```text
REF: x1 = 0xffffffff
DUT: x1 = 0x00000fff
```

DiffTest 可以在首个可观察差异处报告：

```text
旧 PC 和下一 PC 相同；当前指令是 addi x1, x0, -1
x1: REF = 0xffffffff，DUT = 0x00000fff
```

这把问题从“整个处理器为什么不对”缩小到“这条指令附近为什么出现状态差异”。**首个差异是调查起点，不一定是根因**；错误也可能来自更早的未比较状态，必要时回看前几条指令和未比较的状态。波形仍然有用，但主要用于继续查看内部信号，而不是让眼睛承担整套参考模型的工作。

DiffTest 还能自动重复运行大量测试程序。每次测试都从相同初始状态开始，发现差异后保存输入和日志，就能复现问题。

## 5. DiffTest 也有边界

不能因为有 DiffTest 就声称“处理器已经完全正确”：

- **测试激励不足**：没执行到的指令和边界情况不会暴露问题。
- **REF 也可能错误**：REF 需要结合 ISA 手册、独立测试集或其他参考实现校验；给 DUT 注入 bug 不能证明 REF 符合 ISA。
- **共同误解**：如果 DUT 和 REF 都照抄同一个错误理解，比较可能一致但仍不符合 ISA。
- **比较边界不合理**：把不同时间点的状态拿来比较，会产生大量伪差异。
- **只比较部分状态**：未覆盖的内存或控制状态仍可能藏有错误。

针对“接口未接入、比较被跳过”等假通过问题，P2 会正式要求主动给 DUT 注入一个已知 bug，验证 DiffTest 确实能够发现它。本单元晚间实验可以先做一次预演，但它不是校验 REF 的手段。

4. REF 是否一定正确？为什么？
5. 为什么“所有已有测试通过”仍不能证明处理器支持的情况都正确？
6. 为什么要主动注入一个已知 bug？
7. 如果 REF 和 DUT 对同一条指令犯了相同错误，DiffTest 会怎样？

## 8. 晚间实验衔接

建议按以下顺序推进，而不是同时调试所有模块：

1. 先让 minirvEMU 正确执行一个小程序，打印每条指令的旧 PC、下一 PC 和寄存器变化。
2. 再让 RTL minirv NPC 执行同一程序。
3. 先人工对齐少量指令的状态，再讨论自动 DiffTest 接口。
4. 可选预演：自动比较跑通后，注入一个你预测的 bug，确认报告与预测一致；这项在 P2 才是正式要求。
