# P0 日间学习 03：模拟器与 DiffTest

> 建议用时：20~25 分钟。本单元不需要服务器。
>
> 学完目标：能解释模拟器的主循环、DUT/REF 的职责，以及 DiffTest 为什么能缩小调试范围。

## 1. 模拟器也是一个状态机

指令集模拟器不是“假装打印几条日志”，而是用软件维护 ISA 状态，并逐条执行状态转移。

一个最小主循环可以抽象为：

```text
while 尚未结束:
    1. 从 PC 指向的内存取出指令
    2. 译码，得到操作类型、寄存器编号和立即数
    3. 保存当前 PC，并按规则计算下一 PC
    4. 执行运算、访存或跳转
    5. 提交寄存器、内存和 PC 的变化
```

P0 的 minirvEMU 只实现 8 条指令，但基本结构已经和支持完整 RV32IM 的模拟器一致。增加指令主要是扩展译码与执行规则，不是改变“模拟器是什么”。

实现时尤其要小心 PC：普通指令默认前进 4，`jalr` 则覆盖为跳转目标；`rd` 所需的返回地址来自当前指令的 PC，而不是更新后的 PC。

## 2. DUT 和 REF 分别是什么

在 P0 的验证场景中：

- **DUT（Device Under Test）**：被测设计，也就是用 RTL 实现的 minirv NPC。
- **REF（Reference Model）**：参考模型，也就是按同一 ISA 规则运行的模拟器。

```text
                 相同程序和初始状态
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
        RTL NPC（DUT）            minirvEMU（REF）
             │                         │
             └────── 比较体系结构状态 ──┘
                          │
                    首个差异即报错
```

REF 不是“永远正确的真理”。它是独立实现的一份参考规则，同样可能写错。价值在于：两个不同实现若对同一输入产生不同结果，就给出了一个需要调查的明确位置。

## 3. DiffTest 怎样工作

一种适合当前单周期/迷你处理器的比较流程是：

1. 给 DUT 和 REF 装载相同程序，并设置一致的初始状态。
2. 让 DUT 完成并提交一条指令。
3. 让 REF 执行对应的一条指令。
4. 在指令提交边界比较 PC、通用寄存器，以及定义好的内存写入事件。
5. 如果出现差异，立即停止并报告当前指令和状态；否则继续下一条。

关键是**对齐比较边界**。流水线内部信号、某个中间周期的寄存器值，未必能和模拟器的逐步执行一一对应；应该先比较指令退休后软件可见的体系结构状态。

内存也不必每执行一条指令就完整复制比较一遍。可以先记录 store 的地址、数据和字节使能，在明确的事件边界检查副作用；具体方案由后续实验根据接口决定。

## 4. 为什么比单纯看波形高效

假设 DUT 错误地把 `addi` 的 12 位立即数做了零扩展：

```asm
addi x1, x0, -1
```

正确 REF 与错误 DUT 的结果为：

```text
REF: x1 = 0xffffffff
DUT: x1 = 0x00000fff
```

DiffTest 可以在第一条出错指令处报告：

```text
PC 相同，x1 不同；当前指令是 addi x1, x0, -1
```

这把问题从“整个处理器为什么不对”缩小到“这条指令的立即数或执行路径为什么不对”。波形仍然有用，但主要用于继续查看内部信号，而不是让眼睛承担整套参考模型的工作。

DiffTest 还能自动重复运行大量测试程序。每次测试都从相同初始状态开始，发现差异后保存输入和日志，就能复现问题。

## 5. DiffTest 也有边界

不能因为有 DiffTest 就声称“处理器已经完全正确”：

- **测试激励不足**：没执行到的指令和边界情况不会暴露问题。
- **REF 也可能错误**：两边需要结合手册、测试集和 bug 注入持续校验。
- **共同误解**：如果 DUT 和 REF 都照抄同一个错误理解，比较可能一致但仍不符合 ISA。
- **比较边界不合理**：把不同时间点的状态拿来比较，会产生大量伪差异。
- **只比较部分状态**：未覆盖的内存或控制状态仍可能藏有错误。

因此，P2 会要求主动给 DUT 注入一个已知 bug，验证 DiffTest 确实能够发现它，而不是只显示“通过”。

## 8. 晚间实验衔接

建议按以下顺序推进，而不是同时调试所有模块：

1. 先让 minirvEMU 正确执行一个小程序，打印每条指令的 PC 和寄存器变化。
2. 再让 RTL minirv NPC 执行同一程序。
3. 先人工对齐少量指令的状态，再讨论自动 DiffTest 接口。
4. 自动比较跑通后，注入一个你预测的 bug，确认报告与预测一致。
