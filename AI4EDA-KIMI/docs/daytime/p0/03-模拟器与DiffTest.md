# P0 日间学习 03：模拟器与 DiffTest

> 建议用时：20~25 分钟。本单元不需要服务器。
>
> 官方讲义：[E4 RTL 仿真与 DiffTest](https://ysyx.oscc.cc/docs/2607/e/4.html)、[E5 迷你 RISC-V 处理器](https://ysyx.oscc.cc/docs/2607/e/5.html)。本单元沿用官网的 `sEMU/sCPU → minirvEMU/NPC → DiffTest` 路径。
>
> 学完目标：能解释模拟器的主循环、DUT/REF 的职责，以及 DiffTest 为什么能缩小调试范围。

## 1. 为什么不能一直只看波形

官网 E4 给出了一个很直观的规模估计：如果 NPC 有 1000 个信号，程序在 100000 个周期后出错，波形中可能包含一亿个信号值。逐个翻找不仅慢，也很难判断哪个值才对应 ISA 层面的错误。

处理器的工作本质上是逐条执行指令。因此可以换一个思路：

```text
用另一种更简单的方式实现同一个 ISA
                ↓
让两种实现执行相同程序和初始状态
                ↓
比较每条指令提交后的软件可见状态
```

这就是 DiffTest 的出发点。波形并没有被淘汰，而是用于发现状态差异后继续定位内部原因。

## 2. 指令集模拟器：可以执行程序的程序

官网 E4 先用 C 语言实现 `sEMU`，E5 再实现 `minirvEMU`。它们都用 C 程序的状态机实现 ISA 状态机：

| ISA 中的内容 | C 程序中的对应实现 |
|---|---|
| PC | 一个保存指令地址的变量 |
| GPR | 一个寄存器数组 |
| 内存 | 一个保存指令和数据的数组 |
| 指令语义 | 取指、译码、执行和提交状态的语句 |

一个最小主循环可以抽象为：

```text
while 尚未遇到 ebreak:
    1. 从当前 PC 指向的内存取出指令
    2. 译码，得到操作类型、寄存器编号和立即数，并读取 rs1/rs2 的值
    3. 保存旧 PC
    4. 执行运算或访存，并按指令类型决定下一 PC
    5. 统一提交寄存器、内存和 PC 的变化
```

官网 E4 的 `inst_cycle()` 与这里的结构一致。P0 的普通指令默认前进 4，`jalr` 则覆盖为跳转目标；`rd` 的返回地址来自旧 PC。完整 RV32I 中，分支和 `jal` 也会改变下一 PC。

P0 的 minirvEMU 只实现 8 条指令，但主循环骨架与完整模拟器相似。完整 RV32IM 还要扩展其他分支与跳转、乘除法、异常和调试功能，P1 的 NEMU 会大得多。`ebreak` 按官网 E5 作为停机约定，DUT/REF 看到它都应停止。

## 3. DUT 和 REF 分别是什么

官网 E4 最早的配对是：

- **DUT（Design Under Test）**：被测设计，即用 RTL 实现的 sCPU。
- **REF（Reference）**：参考实现，即用 C 实现的 sEMU。

本项目先把这条路径跑通，再延伸到 **minirv NPC（DUT）↔ minirvEMU（REF）**：

```text
                 相同程序和初始状态
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
        RTL NPC（DUT）            minirvEMU（REF）
             │                         │
             └────── 比较体系结构状态 ──┘
                          │
                    首个差异即报错
```

REF 不是“永远正确的真理”。它是另一份实现，同样可能写错；P0 里两份实现都由你自己完成，独立性也有限。两个实现产生不同结果时，说明这里需要调查，但不能只凭差异断定必然是 DUT 错。

## 4. DiffTest 怎样进行锁步比较

官网 E4 的核心流程是：sCPU 执行一条指令后，马上让 sEMU 执行一条，再比较 GPR；随后还要求把 PC 纳入比较，因为错误的跳转可能只改变 PC。

一种适合当前单周期/迷你处理器的流程是：

1. 给 DUT 和 REF 装载相同程序，并设置一致的初始状态。
2. 让 DUT 完成并提交一条指令。
3. 让 REF 执行对应的一条指令。
4. 在指令提交（retire，退休）边界比较退休后的下一 PC、通用寄存器，以及定义好的内存写入事件。
5. 如果出现差异，立即停止并报告；否则继续下一条。

这种逐条对齐的方式称为**锁步（lockstep）比较**。如果 DUT 并非每周期退休一条指令，就不能简单每个时钟都调用一次 REF，而要等 DUT 的指令提交事件。

两端必须采用同一个 PC 定义，日志建议同时打印旧 PC 和下一 PC。内存可先记录 store 的地址、数据和字节使能；若方便，也可用 mtrace 记录 load 地址，否则“load 地址算错但碰巧读到相同数据”会成为比较盲区。

## 5. 首个差异怎样帮助定位

假设 DUT 错误地把 `addi` 的 12 位立即数做了零扩展：

```asm
addi x1, x0, -1
```

比较报告可以写成：

```text
旧 PC 和下一 PC 相同；当前指令是 addi x1, x0, -1
x1: REF = 0xffffffff，DUT = 0x00000fff
```

这把调查范围从整个处理器缩小到这条指令附近。**首个可观察差异是调查起点，不一定是根因**；错误也可能来自更早的未比较状态，必要时回看前几条指令。

官网 E4 还安排了一个重要实验：主动给 sCPU 注入错误，观察 DiffTest 能否报告，并补充 PC 和不一致寄存器等报错信息。本项目 P0 可以预演，P2 再在完整 NPC/NEMU 基础设施上正式完成。

## 6. DiffTest 的边界

不能因为有 DiffTest 就声称“处理器已经完全正确”：

- **测试激励不足**：没执行到的指令和边界情况不会暴露问题。
- **REF 也可能错误**：REF 需要结合 ISA 手册、独立测试集或其他参考实现校验；给 DUT 注入 bug 不能证明 REF 符合 ISA。
- **共同误解**：如果 DUT 和 REF 都照抄同一个错误理解，比较可能一致但仍不符合 ISA。
- **比较边界不合理**：把不同时间点的状态拿来比较，会产生大量伪差异。
- **只比较部分状态**：未覆盖的内存、load 地址或控制状态仍可能藏有错误。

因此，bug 注入用于验证比较机制能发现已知错误，避免“接口未接入、比较被跳过”等假通过；它不是校验 REF 的手段。

## 7. 自测题

1. 指令集模拟器如何用 C 程序的状态实现 ISA 的状态？
2. 为什么应在指令提交边界比较，而不是随意挑一个内部周期？
3. 为什么只比较 GPR 还不够，还要比较 PC？
4. 如果 DUT 不是每周期退休一条指令，REF 应该何时执行？
5. 为什么要主动注入一个已知 bug？它能证明 REF 正确吗？
6. 如果 REF 和 DUT 对同一条指令犯了相同错误，DiffTest 会怎样？

<details>
<summary>参考答案（先自己回答，再展开）</summary>

1. 用变量实现 PC，用数组实现 GPR 和内存，用 C 语句实现取指、译码、执行和状态提交。
2. 提交后的 ISA 状态有明确对应关系；内部周期和中间信号取决于微架构，未必能直接对齐。
3. 跳转等错误可能只改变 PC，GPR 暂时一致，遗漏 PC 会延迟或漏掉错误。
4. 等 DUT 每次提交一条指令后，再让 REF 执行对应的一条，保持锁步。
5. 用来证明比较机制能发现已知错误，避免假通过；它不能证明 REF 正确。
6. 两边状态可能仍然一致，DiffTest 会通过，但实现仍不符合 ISA，因此还需要手册、独立测试和不同来源的参考实现。

## 9. 晚间实验衔接

按[官网 E4](https://ysyx.oscc.cc/docs/2607/e/4.html)和 E5 的顺序推进，不要同时调试所有模块：

1. 先让 sEMU 或 minirvEMU 正确执行一个小程序，打印旧 PC、下一 PC 和寄存器变化。
2. 再让对应 RTL 执行同一程序，先人工对齐少量指令的状态。
3. 自动锁步比较跑通后，再注入一个你预测的 bug，确认报告与预测一致。
4. 把实验结果写入 [P0 ISA 学习笔记](../../p0-isa-notes.md)的“模拟器与 DiffTest 实验记录”小节。

如果前两步尚未完成，今晚不必急着做自动 DiffTest；先确保自己理解每条指令的状态转移。
