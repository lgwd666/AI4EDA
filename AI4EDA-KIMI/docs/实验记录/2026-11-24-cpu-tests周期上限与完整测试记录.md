## 2. 前置问题与处理状态

### 2.1 统一存储器与初始化数据

此前 `riscv-tests/add` 因 `.rodata` 只进入指令区、LSU 数据区仍为零而误判失败。

已完成：

- DUT 的 `imem/dmem` 合并为统一 `pmem`；
- REF 的取指和数据访问统一使用 `memory_`；
- IFU 和 LSU 共用 `pmem_read()`，均传入完整 CPU 地址；
- 环境根据 `0x80000000` 基址计算 SRAM 局部偏移。

对应提交：

```text
7090035 合并DUT与参考模型的指令数据存储器
4243634 统一取指与数据读取接口
```

### 2.2 LBU 负地址偏移

此前 `lbu gp,-16(sp)` 将 `12'hff0` 零扩展为 `+4080`，而不是符号扩展为 `-16`。

本人已将 LOAD/STORE 的地址计算统一为：

```systemverilog
assign mem_addr =
    (opcode==STORE)||(opcode==LOAD) ?
        rs1_data + {{20{imm[11]}}, imm[11:0]} :
        32'b0;
```

同时保留 LBU 读出字节的零扩展：

```systemverilog
{24'b0, mem_rdata_lb}
```

修复后 `riscv-tests/add` 已输出：

```text
HIT GOOD TRAP: pc=0x800033c8, a0=0
[           add] PASS
```

### 2.3 hello-str 与预编译 klib

`hello-str` 最初输出：

```text
HIT BAD TRAP: pc=0x800002ec, a0=0x00000001
```

原因不是 NPC 指令错误，而是本地 klib 中：

```c
int sprintf(char *out, const char *fmt, ...) {
  panic("Not implemented");
}

int strcmp(const char *s1, const char *s2) {
  panic("Not implemented");
}
```

`panic()` 调用 `halt(1)`，所以最终 `a0=1`。同时 `putch()` 是空函数，因此终端看不到 `AM Panic` 文本。

本次测试前已下载官方预编译库：

```text
https://ysyx.oscc.cc/slides/resources/archive/klib-minirv-npc.tar.bz2
```

解压到：

```text
abstract-machine/klib/build/klib-minirv-npc.a
```

由于压缩包中的归档时间戳早于本地 klib 源码，执行了：

```bash
touch abstract-machine/klib/build/klib-minirv-npc.a
```

避免 `make` 使用本地未实现源码重新构建并覆盖预编译库。

使用后，`hello-str` 已通过：

```text
HIT GOOD TRAP: pc=0x8000031c, a0=0
[     hello-str] PASS
```

### 2.4 wrong 是故意失败的测试

`tests/wrong.c` 的内容是：

```c
int main() {
  return 1;
}
```

因此它必然执行：

```text
a0=1 → ebreak → HIT BAD TRAP → ***FAIL***
```

这个负向测试用于验证 BAD TRAP 和失败退出码传递，不应该通过修改源码消除失败。

## 3. 周期不足问题

### 3.1 matrix-mul

初始结果：

```text
NPC TEST FAIL: ebreak not reached, pc=0x80000634
```

停止位置在软件乘法函数 `__mulsi3` 中。

`10×10` 矩阵乘法包含 1000 次乘法。当前 NPC 没有 M 扩展，乘法通过软件移位和累加完成；minirv 又将移位、逻辑运算等展开成大量查表指令，因此 100 万周期不足。

### 3.2 narcissistic

初始结果：

```text
NPC TEST FAIL: ebreak not reached, pc=0x800008e8
```

停止位置在 `__hidden___udivsi3` 的除法代码中。

程序遍历 `100～499`，每轮执行除法、取余和立方计算，包含大量软件乘除法。100 万周期内尚未执行到 `ebreak`。

### 3.3 prime

初始结果：

```text
NPC TEST FAIL: ebreak not reached, pc=0x80000b10
```

停止位置同样在 `__hidden___udivsi3` 中。

程序对 `101～149` 的奇数反复执行：

```c
m % i
```

对于素数，内层循环会一直执行到 `i == m`，需要大量软件取余。

### 3.4 共同特征

这三个程序失败时都有以下特征：

- 没有 `DIFFTEST FAIL`；
- 没有 `HIT BAD TRAP`；
- 输出都是 `NPC TEST FAIL: ebreak not reached`；
- PC 位于软件乘法或除法函数，而不是 `check()` 或 `fail`。

这说明当时程序尚未报告计算错误，主要问题是仿真周期预算不足。

## 4. 修改周期上限

修改 `npc/csrc/main.cpp`：

```cpp
// 修改前
constexpr uint64_t max_cycles = 1000000;

// 修改后
constexpr uint64_t max_cycles = 100000000;
```

该修改只改变仿真器允许执行的最大周期数，不改变：

- NPC RTL；
- 指令语义；
- PC、寄存器或存储器；
- DiffTest 比较规则；
- GOOD/BAD TRAP 判断规则。

`100000000` 是允许执行的上限，不代表每个测试实际消耗了这么多周期。本次没有增加逐测试周期计数，因此不能据此给出每项测试的最小周期需求。

## 7. 结果说明

### 7.1 周期不足已经得到验证

提高上限后，`matrix-mul`、`narcissistic`、`prime` 都由：

```text
NPC TEST FAIL: ebreak not reached
```

变为：

```text
HIT GOOD TRAP / PASS
```

因此可以确认，这三个程序此前的失败是仿真周期预算不足，不是已经证实的计算功能错误。

### 7.2 recursion 已通过

此前 `recursion` 曾被列为需要重新检查的项目。本次完整测试中：

```text
HIT GOOD TRAP: pc=0x80000c1c, a0=0
```

因此在当前统一存储器、LBU 修复和预编译 klib 环境下，该项已经通过。

### 7.3 cpu-tests/div 与 riscv-tests/div 不同

本次 `cpu-tests` 中的 `div` 是 C 测试程序，编译后通过 `__divsi3`、`__modsi3` 等软件函数完成除法，本次已经 PASS。

此前 `riscv-tests` 中的 `div` 则直接包含：

```asm
div x14, x1, x11
```

它要求 RISC-V M 扩展。当前 `minirv-npc` 使用：

```text
-march=rv32e_zicsr -mabi=ilp32e
```

NPC 和 REF 也没有实现硬件 DIV，因此该测试仍不属于当前 8 指令 minirv 的支持范围。

两个同名测试不能混为一谈。

### 7.4 wrong 不影响正向测试结论

`wrong` 的 FAIL 是测试设计的一部分。它验证了：

- `a0 != 0` 时仿真器输出 BAD TRAP；
- 失败状态能够传递给 AM/Makefile；
- 测试框架能够区分成功和失败程序。

因此完整结果应表述为“35 项正向测试全部通过，负向测试行为正确”，而不是“36 项全部 PASS”。
