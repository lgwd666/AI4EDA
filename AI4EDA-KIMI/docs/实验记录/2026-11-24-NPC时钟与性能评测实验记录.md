# NPC 时钟与性能评测实验记录

> 日期：2026-11-24  
> 阶段：一生一芯 E6  
> 官方讲义：[E6：异常处理和输入输出](https://ysyx.oscc.cc/docs/2607/e/6.html)  
> 对应章节：添加 UART 支持字符输出、添加时钟支持计时功能、性能评测入门、NPC 中流逝的时钟

## 1. 实验目标

在已有 minirv NPC、minirvEMU 和 DiffTest 的基础上，完成以下工作：

1. 梳理并验证 UART 字符输出链路。
2. 添加基于 MMIO 的 64 位计时器，让 AM 程序可以读取微秒级时间。
3. 计时值由 NPC 已执行的仿真周期数换算，不使用宿主机墙钟时间。
4. 保证 DUT 和 REF 读取计时器时不会因为周期边界不同而产生 DiffTest 假差异。
5. 使用 `archbench` 的 `train` 输入进行性能测试，并验证 100MHz 与 1000MHz 假设下的分数换算关系。

本次没有修改 NPC RTL，也没有实现 UART 状态寄存器、键盘、显示器或真实 RTC 日期功能。

## 2. 总体结构

```text
archbench / am-kernels 中的 C 程序
              |
              v
  AM + minirv-gcc 编译、链接，生成 .bin
              |
              v
+-------------NPC 仿真环境----------------+
|                                         |
|  DUT: minirv NPC <---- DiffTest ---- REF |
|     |                         minirvEMU |
|     |                              |    |
|     +-------- 指令逐条对比 ---------+    |
|     |                                   |
|     +-- IFU/LSU -> pmem_read/write()    |
|                       |                 |
|          +------------+------------+    |
|          |                         |    |
|      PMEM 128 MiB              MMIO 设备|
|          |                    |         |
|   0x80000000 起始       0x10000000 UART |
|                         0x20000000 时钟 |
+-----------------------------------------+
```

UART 和时钟都是仿真环境中的行为模型。处理器仍然只执行普通的 `lw/sw/lbu/sb` 等访存指令，通过地址区分存储器和设备，不需要新增指令。

## 3. UART 输出链路

### 3.1 软件侧

`abstract-machine/am/src/riscv/npc/trm.c` 中的 `putch()` 使用 `volatile` 指针写 UART 数据寄存器：

```c
void putch(char ch) {
  *(volatile char *)0x10000000 = ch;
}
```

`volatile` 防止编译器删除或合并设备访问。以 `hello` 程序为例，反汇编可以看到其核心访问为：

```asm
lui  a5, 0x10000
sb   a0, 0(a5)    # 向 0x10000000 写入一个字符
```

### 3.2 仿真侧

`npc/csrc/pmem.cpp` 的 `pmem_write()` 识别 `0x10000000`，把 `wdata` 低 8 位写到 `stderr`；其他地址仍按字节掩码写入 PMEM。

当前 LSU 的组合逻辑 DPI 调用在一次 Verilator 求值中可能重复出现，甚至在信号尚未稳定时出现瞬态写调用。仿真环境因此采用“低电平观察写请求、高电平最多提交一次”的周期写窗口，不读取 PC 或指令编码；UART 和 PMEM 共用该提交规则。完整定位过程见[UART 重复输出与周期写提交调试记录](2026-11-24-UART重复输出与周期写提交调试记录.md)。

REF 执行到 UART 的 `sb` 时忽略设备写，避免再次打印字符，也避免把设备地址当作 PMEM 地址。

验证命令：

```bash
cd AI4EDA-KIMI/ysyx-workbench/am-kernels/kernels/hello
make ARCH=minirv-npc run
```

验证结果：

```text
Hello, AbstractMachine!
mainargs = ''.
HIT GOOD TRAP
```

## 4. 周期计时器

### 4.1 MMIO 地址约定

| 地址 | 方向 | 含义 |
|---|---|---|
| `0x20000000` | 读 | 已流逝微秒数的低 32 位 |
| `0x20000004` | 读 | 已流逝微秒数的高 32 位 |

`npc/csrc/pmem.cpp` 中的 `pmem_read()` 对上述两个地址返回计时值，不再进入 PMEM 地址偏移计算。

### 4.2 用周期数换算时间

仿真环境维护 `cycle_count`，每执行完一条 DUT/REF 对比的指令后调用一次 `pmem_tick()`：

```cpp
uint64_t cycle_count = 0;
constexpr uint64_t kCyclesPerMicrosecond = 100;  // 100MHz

uint64_t get_time() {
  return cycle_count / kCyclesPerMicrosecond;
}
```

100MHz 表示每微秒 100 个周期，因此：

```text
设备时间(us) = 已执行周期数 / 100
```

这里测量的是 NPC 内部时间，与宿主机运行 Verilator 实际花了多少秒无关。把常数改为 `1000` 即模拟 1000MHz；在周期数不变的情况下，设备时间变为原来的十分之一。

### 4.3 为什么 `pmem_tick()` 放在 DiffTest 之后

DUT 执行 `lw` 读取计时器，REF 也必须读取同一个值。如果 DUT 读完后立即增加周期，REF 再读取，两者在低 32 位发生进位时可能不同。

当前 `main.cpp` 的顺序为：

```text
记录当前指令
    -> DUT 执行一个周期
    -> REF 执行同一条指令并比较 PC/GPR
    -> pmem_tick()
```

`minirv_emu.cpp` 对计时器地址的 `read32()` 调用同一个 `pmem_read()`。这样 DUT 和 REF 在同一个逻辑周期边界读取计时器，避免由仿真实现顺序造成的假差异。

### 4.4 AM 的 64 位读取

`abstract-machine/am/src/riscv/npc/timer.c` 的 `__am_timer_uptime()` 通过两次 `lw` 读取低、高 32 位，并采用“高—低—高”顺序：

```c
do {
  high_before = *timer_high;
  low = *timer_low;
  high_after = *timer_high;
} while (high_before != high_after);

uptime->us = ((uint64_t)high_before << 32) | low;
```

如果读取低 32 位期间发生向高 32 位进位，两次高位值会不同，此时重新读取，避免拼出一个从未出现过的 64 位时间。

## 5. 时钟功能验证

运行官方 AM 时钟测试：

```bash
cd AI4EDA-KIMI/ysyx-workbench/am-kernels/tests/am-tests
NPC_MAX_CYCLES=110000000 make ARCH=minirv-npc run mainargs=t
```

观察结果：

```text
1900-0-0 00:00:00 GMT (1 second).
NPC TEST FAIL: ebreak not reached
```

分析：

- `(1 second)` 表明周期计数、微秒换算和 AM 读取链路已经工作。
- `rtc_test()` 本身是无限循环，不会执行到 `ebreak`，所以随后达到周期上限并返回非零是预期现象，不代表计时功能失败。
- 默认上限为 1 亿周期，在 100MHz 下刚好对应 1 秒；程序还需要额外执行判断和输出指令，因此验证时把上限提高到 1.1 亿。
- 日期全为零是因为本次只实现 `AM_TIMER_UPTIME`，没有实现真实 RTC 日期。

`NPC_MAX_CYCLES` 是新增的仿真环境变量，默认值为 `100000000`，较长程序可这样设置：

```bash
NPC_MAX_CYCLES=1000000000 make ARCH=minirv-npc run
```

## 6. 性能测试方法

### 6.1 为什么使用 `train`

`test` 输入主要用于快速验证功能，循环次数和数据量较小，计时可能仍为 `0 ms`，不适合作为代表性性能结果。`train` 输入具有更明确的计算负载，适合 RTL 仿真环境中的微结构和性能比较。

完整套件通常同时报告：

- 每个程序的相对分数和耗时；
- 所有分数的算术平均值；
- 所有分数的几何平均值，通常以几何平均值作为综合性能指标。

比较不同 NPC 版本时，必须保持 benchmark、输入规模、编译选项和假设频率一致。

### 6.2 单项测试流程

以 `101.igemm` 为例：

```bash
cd AI4EDA-KIMI/ysyx-workbench/archbench/bench/101.igemm
BENCH_HOME=/home/lgwd666/work/work/AI4EDA/AI4EDA-KIMI/ysyx-workbench/archbench \
NPC_MAX_CYCLES=1000000000 \
make ARCH=minirv-npc run mainargs=train
```

注意：`BENCH_HOME` 必须指向 `archbench` 根目录，不能指向当前 benchmark 子目录，否则 `Makefile` 会递归包含自身。

程序输出的关键字段：

- `Dot product ... took ... us`：被测核心计算的设备时间。
- `[RESULT] PASS`：功能校验通过。
- `min time`：用于计分的最短时间。
- `Marks`：相对于参考处理器的分数。
- `Total time`：包含准备、校验等工作的总设备时间。
- `HIT GOOD TRAP`：程序正常结束。

### 6.3 100MHz 与 1000MHz 对比

同一个 `igemm-minirv-npc.bin`、同一 `train` 输入，仅修改 `kCyclesPerMicrosecond` 并重新编译仿真器：

| 假设频率 | 核心计算时间 | 计分时间 | 总设备时间 | 分数 | 结果 |
|---|---:|---:|---:|---:|---|
| 100MHz | 3,069,509 us | 3,069,514 us | 3,681,912 us | 7 Marks | PASS / GOOD TRAP |
| 1000MHz | 306,951 us | 306,951 us | 368,174 us | 71 Marks | PASS / GOOD TRAP |

计分时间从约 3.0695 秒降为约 0.3070 秒，基本正好缩小 10 倍；分数从 7 提高到 71，约为 10 倍。分数不是严格等于 70，是因为程序输出和计分过程中存在整数取整。

这验证了：

```text
相同程序 -> 相同指令数/周期数
频率提高 10 倍 -> 设备时间约缩小 10 倍 -> 相对性能分数约提高 10 倍
```

这里的 100MHz 和 1000MHz 都只是性能模型的假设，不代表当前 RTL 已通过综合或时序收敛，也不代表实际芯片可以工作在 1000MHz。

## 9. 结论与后续工作

本次已经打通“程序执行周期 -> MMIO 微秒时间 -> AM benchmark -> 相对性能分数”的完整链路。UART 输出正确，时钟测试能够到达 1 秒，`igemm train` 在两种假设频率下均通过功能和 DiffTest 验证，频率—时间—分数的换算关系符合预期。

后续可以进行：

1. 安装完整脚本依赖，运行全部 `archbench train`，记录几何平均分作为后续微结构优化的基线。
2. 每次修改 NPC 后，先运行功能回归，再在相同频率和输入下比较性能。
3. 通过综合和静态时序分析获得更可信的最高频率，替换当前人为假设的频率。
4. 按讲义继续添加 UART 状态寄存器，并处理其随机状态在 DiffTest 中的同步。
